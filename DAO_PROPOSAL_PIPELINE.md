# 🧭 Compilatorum — DAO Proposal Pipeline

> **Purpose:** reframe the Compilatorum portfolio from a collection of heterogeneous repositories into a regenerative pipeline of infrastructure → construct → MVP → proposal → funding → artifact → reputation → new proposal.

## 0. Executive decision

The current GitHub state contains **42 repositories**, not ~36. The portfolio should therefore not be optimized as a conventional freelance portfolio. It should be treated as a **research-and-proposal ecosystem**.

Core principle:

`explore freely → compress rigorously → propose selectively → execute organically`

The DAO/grant layer is a **selection and coordination mechanism**, not an obligation to create a DAO around every project.

## 1. Target ontology

### 1.1 Repository roles

- **INFRA** — reusable substrate, tooling, orchestration, knowledge, data, UI, or governance infrastructure.
- **CONSTRUCT** — coherent intellectual/technical hypothesis that can evolve into an initiative.
- **MVP** — construct with a sufficiently bounded demonstrator or product surface.
- **PROPOSAL** — construct with enough problem definition, evidence, artifact, impact hypothesis, roadmap and budget to seek external funding.
- **RESEARCH** — valuable exploratory work whose uncertainty is still too high for proposalization.
- **ARCHIVE** — historical, redundant, placeholder, or low-leverage material retained for provenance but not actively developed.
- **BRIDGE** — a repository whose main value is connecting other projects or translating between layers.

A repository may have a **primary role** and a **secondary role**. Roles are deliberately not permanent.

## 4. Proposal funnel

The Compilatorum should use the following state machine:

`IDEA → RESEARCH → CONSTRUCT → MVP → EVIDENCE → PROPOSAL-READY → FUNDED → EXECUTING → ARTIFACT → IMPACT → REPUTATION → NEXT PROPOSAL`

A construct is **not required to reach the end**. Every transition produces reusable capital:

- failed hypothesis → knowledge;
- prototype → evidence;
- dataset → research capital;
- UI → communication capital;
- proposal → coordination capital;
- funded project → social/technical capital.

## 5. Proposal-readiness function

Use a qualitative score:

`R = 0.20I + 0.15P + 0.15E + 0.15M + 0.15C + 0.10L + 0.10H`

Where:

- `I` = importance/impact;
- `P` = problem clarity;
- `E` = empirical/technical evidence;
- `M` = MVP maturity;
- `C` = community/coordination potential;
- `L` = leverage/reusability;
- `H` = homeostatic/ergonomic fit.

The last term is deliberate. A project with high market potential but poor sustainability for the builder should **not automatically win**.

Suggested gates:

- `R < 0.45` → research/parking;
- `0.45 ≤ R < 0.65` → construct development;
- `0.65 ≤ R < 0.80` → MVP/evidence;
- `R ≥ 0.80` → proposal candidate.

These thresholds are heuristics, not scientific measurements.

## 8. Portfolio rule

The public-facing portfolio should show **initiatives and capabilities**, not 42 unrelated repositories.

Recommended presentation:

`4–6 initiative families`

↓

`10–15 flagship artifacts`

↓

`repository evidence`

↓

`proposal/grant opportunities`

The repository graph remains the technical appendix.

## 9. Anti-fragmentation invariant

Do **not** create:

`1 project → 1 DAO → 1 token → 1 governance system`

by default.

Prefer:

`many constructs → few proposal families → shared infrastructure → selective funding`

The DAO layer should reduce fragmentation, not institutionalize it.

## 10. Ergonomic invariant

The portfolio is an adaptive ecology, not a demand-generation machine.

`cashflow gigs` may exist as a liquidity layer, but they are not the primary ontology of work.

The preferred loop is:

`curiosity → exploration → compression → proposal → funding → focused execution → integration → recovery`

rather than:

`client → deadline → context switch → delivery → new client`
